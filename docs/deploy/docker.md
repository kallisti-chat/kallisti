# Docker and Podman deployment

For installation commands, use [Installing with Docker or Podman](../install-docker.md). Run Compose from the repository root. The Compose files in `deploy/` support the built-in Mumble server with Caddy (`compose.yml`), the same server with Cloudflare DNS-01 and no published HTTP port 80 (`compose.yml` plus `compose.dns01.yml`), an external Murmur with Caddy (`compose.murmur.yml`), or an existing reverse proxy (`compose.behind-proxy.yml`). Only run one variant per installation. Each variant builds Kallisti from the source, or pulls the published image with `compose.published.yml` on top (see [published images](../install-docker.md#published-images-instead-of-a-build)).

## Traffic and data

- Caddy serves HTTPS on TCP 443. The base and Murmur variants redirect TCP 80; the DNS-01 variant does not publish that port. The app listens only inside the Compose network on 8080; Caddy forwards ordinary requests and WebSockets. The existing-proxy variant must attach to the proxy network and configure that proxy to reach `kallisti:8080` and set `X-Forwarded-For`.
- The built-in Mumble server exposes TCP and UDP 64738 directly. External Murmur handles its own Mumble port; no Mumble port is published by that Compose variant.
- Kallisti runs without root access and writes its SQLite database, uploads, daily database backups and self-signed fallback certificate in `/data`. `cert-sync` runs as root because Caddy's private key is private and the app's data belongs to another user. It reads Caddy storage only and writes the app's data volume; neither the app nor Caddy gets the Docker socket.
- Compose drops all helper-container capabilities, then grants Caddy `NET_BIND_SERVICE` to bind ports and `DAC_OVERRIDE` to read private operator-owned configuration/token files. The copier gets only `CHOWN`, `DAC_OVERRIDE` and `FOWNER` to read private keys and publish files for the app's arbitrary `PUID:PGID`. Existing users, volume ownership and certificate paths stay the same. Custom Caddy modules or configurations needing other privileges require an explicit Compose override.
- The base, DNS-01 and Murmur variants retain the `deploy_` project volumes; the existing-proxy variant retains `kallisti_kallisti-data`. Keep `deploy/.env` in place and preserve any custom Compose project name. Never delete the data volume during an update.

## Certificates and access

Caddy requests and renews the web certificate for `DOMAIN`. For the built-in server with bundled Caddy, `cert-sync` checks every 60 seconds. It copies a certificate only when the name, remaining validity (at least 48 hours) and private key match. It switches the pair together; Kallisti reads the renewed files on each new Mumble TLS connection. Before the first issuance it uses its persistent self-signed certificate. Check `docker compose -f deploy/compose.yml logs cert-sync` if native Mumble clients still see a certificate warning after the website has HTTPS. The existing-proxy variant cannot read an external proxy's certificates: either accept the self-signed Mumble certificate or provide a protected certificate and key under `/data` using `MUMBLE_CERT_FILE` and `MUMBLE_KEY_FILE`.

The DNS-01 override requires Docker Compose 2.24.4 or later for `!override`. Run it with `-f deploy/compose.yml -f deploy/compose.dns01.yml` in that order. It builds Caddy 2.11.7 with the pinned Cloudflare plugin. Its scoped API token comes from an operator-managed file outside the repository, mounted read-only as a Compose secret. Caddy reads it at startup into its process environment; it is not included in `docker compose config`, but Docker administrators can still access it. A missing or empty file stops Caddy. DNS-01 does not need public port 80; HTTP requests to that port will not redirect. Use a DNS-only Cloudflare record if native Mumble or WHIP clients use `DOMAIN` because Cloudflare's web proxy does not forward those ports. See [DNS-01 setup](../install-docker.md#cloudflare-dns-01-without-public-http-port-80) for permissions, token handling, and the startup command.

The external Murmur variant keeps its previous default of accepting self-signed certificates. Set `MUMBLE_INSECURE_TLS=0` in `deploy/.env` when Murmur has a trusted certificate and you want upstream identity checks. Protect `.env`: the SuperUser password is passed as an environment variable and is visible to administrators with Docker access. Docker access also gives access to both data volumes and the certificate key.

Caddy adds HSTS, framing and content-type protections, compresses responses, and limits request bodies to 11 MB for the default 10 MB upload limit. Raise both limits together if uploads need to grow. It does not write access logs because file URLs contain bearer keys. Web traffic must use a public DNS name that resolves to the host and reaches port 443; the default and Murmur variants also require port 80, while the DNS-01 variant does not publish it. For native clients, open both protocols on port 64738. Do not publish Kallisti's internal port 8080.

## Operations

Check the rendered configuration before starting a variant (use both files in order for DNS-01; use the selected single file for other variants):

```sh
docker compose -f deploy/compose.yml config --quiet
docker compose -f deploy/compose.yml up -d --build
docker compose -f deploy/compose.yml ps
docker compose -f deploy/compose.yml logs --tail=100 kallisti caddy cert-sync
```

Run `sh tests/deploy/cert-sync.sh` from the repository root to check certificate validation, renewal and interruption with synthetic certificates; it needs Docker and OpenSSL. For DNS-01, run `sh tests/deploy/dns01.sh` to build the custom Caddy image and check Compose topology, the Cloudflare plugin and Caddyfile with a synthetic token. Neither check proves public ACME issuance.

The cert-sync image healthcheck reads the last completed pass from `mumble-tls/.status` in `APP_DATA_DIR` (default `/app-data`). `current` means a valid matching certificate was copied or was already current. `waiting` is healthy: Caddy has not supplied a certificate yet and Mumble keeps its current or self-signed certificate. `rejected` means certificate material was present but no pair passed validation, including the existing requirement for at least 48 hours of remaining validity. Short-lived certificates may therefore report unhealthy near renewal even while the previously copied certificate still works. A missing heartbeat, an invalid status, or a heartbeat more than five minutes old (or over five minutes in the future) fails the check. Docker marks the container unhealthy after three failed checks; plain Compose does not restart it just for being unhealthy. This reports copier progress, not public HTTPS readiness or the expiry of a previously copied certificate when Caddy's source files disappear.

The status file is cleared on startup and refreshed once per pass; no volume migration or extra writable mount is needed. Older pinned cert-sync images still work with the reduced capabilities but retain their old healthcheck behavior. The new image also works with older Compose files. Kubernetes already runs the helpers as UID 1000 with restricted capabilities; it ignores image healthchecks, and no probe requiring the new executable is added to the chart. This preserves installations that pin an older image. A Podman build using OCI format may omit the image healthcheck; use Docker image format if that metadata is required.

The existing DNS-01 Caddy image healthcheck uses its loopback admin endpoint. If you customize Caddy with `admin off` or move that endpoint, override or disable that healthcheck in Compose. Its result does not prove ACME issuance or public reachability.

The DNS-01 variant retains `cert-sync` and the same Caddy data volume as the base variant. The Murmur variant has no `cert-sync`; the existing-proxy variant has neither `caddy` nor `cert-sync`. The app health check makes Caddy wait for the HTTP server to start, but it does not prove that native clients can connect or that certificate issuance succeeded. Confirm HTTPS in a browser and test a native Mumble connection separately. For backups and restoring the SQLite file and uploads, follow [Backups](../backups.md); copy them off-host, including the persistent Mumble identity certificate. Also keep the Caddy data volume if you need to preserve its ACME account and certificates.

For updates and one-way database migrations, follow [Updating](../updating.md). Before rolling back a binary, restore a database backup from before that version's migration; reverting Compose files alone cannot undo a database migration. If the certificate copier fails, Kallisti keeps its last valid Mumble certificate while it runs. Check its logs and the key's ownership before restarting it. No server or cluster is changed by the files alone.
